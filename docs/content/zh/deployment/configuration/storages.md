# 本地存储

支持 `local`、`shardreel` 和 `telegram`，名称分别显示在 Bot 与网页的存储选择中。

```toml
[[storages]]
name = "本机1"
type = "local"
enable = true
base_path = "./downloads"
```

名称唯一，启用时 `base_path` 必填。容器中使用 `/app/downloads` 对应的挂载目录。用户 `storages` 为允许/排除的名称列表，`blacklist` 控制列表含义。

用 `/storage` 选择默认存储，`/dir` 登记常用相对目录；`/rule` 可以选择已配置的存储。已保存文件不因删除目录登记而删除。网页提供目录浏览和文件下载。

## ShardReel

两个服务可以部署在不同的局域网机器上，数据库各自独立。ShardReel 设置 `SR_STORAGE_API_KEY`（至少 32 字节）及 `SR_STORAGE_ROOT=Telegram`，保持 Worker 启用。Bot 中使用：

```toml
[[storages]]
name = "我的网盘"
type = "shardreel"
enable = true
url = "http://YOUR_SHARDREEL_HOST:8080"
api_key = "YOUR_STORAGE_API_KEY_WITH_AT_LEAST_32_BYTES"
spool_path = "./data/shardreel"
max_pending_bytes = 21474836480
```

`spool_path` 必须位于持久化挂载内，默认在 `data/shardreel/<存储名称>`，待上传空间默认上限 20 GiB。每个存储使用一个后台上传执行器。Telegram 完整下载后进入持久化队列，下载执行槽位释放，最终成功通知和 hook 等待远端入库及 SHA-256 校验。即使启用 `stream`，该后端也使用缓存下载。

两个 Compose 文件均显式挂载 `./shardreel:/app/data/shardreel`。容器重建时保留宿主机的 `data` 和 `shardreel` 目录，停服备份也应同时包含这两个目录。自定义 `spool_path` 到其他位置时需调整对应挂载。

Bot、网页/API 和监听保存媒体组时，在选定的基础目录内按 caption 建立子目录。使用组内消息 ID 最小的有效 caption，清理非法路径字符、控制字符及多余空白，截断为最多 64 个字符且不超过 180 个 UTF-8 字节；不添加消息 ID、日期或随机后缀。同一存储和基础目录下，有效名相同的不同媒体组会保存到同一文件夹，文件重名仍按原策略处理。caption 清理后为空时使用 `album_<聊天ID>_<媒体组ID>`，避免无标题相册混在一起。该规则同时适用于 local 与 ShardReel，不影响 Telegram 聊天间转发。下载缓存及待上传 payload 仍按任务 ID 隔离，数据库记录对应的目标目录。

确认成功后立即删除本地副本；清理失败单独展示并每小时重试，不重新上传。临时失败按 1 分钟、5 分钟、15 分钟、1 小时、3 小时重试，最多 5 次；鉴权、参数及校验错误需要处理。网页任务列表可取消进行中的上传，或删除已结束记录并清理待重试文件；成功成员不会重复上传。失败文件保留至主动删除，空间不足时拒绝新增下载。

远端入库仅在 `can_retry=true` 时自动重试。重试已受理后持续查询实际结果，临时查询失败不会耗尽入库重试预算。“跳过”只保留已入库的同名文件；同名目录或未完成文件会提示处理，不会被报告为已保存。远端接收时再次检查跳过策略，避免检查后出现的同名文件被另存一份。Bot 接受的远端路径最多 2048 个 UTF-8 字节，每级名称最多 512 个字符，不接受控制字符或名称首尾空白。

重启恢复完整落盘的上传，查询原请求后继续；未完整下载的文件需重新下载。停服保留任务。从未发起远端请求的任务取消无需联网；已发起请求的任务需确认远端取消或完成后再清理。在 ShardReel 后台取消待接收的上传也会保留取消回执，Bot 不会重新发起该上传。保存原始字节，播放优化由 ShardReel 的派生缓存承担。

ShardReel 加密格式不接收空文件，该后端会在下载前明确拒绝；空文件仍可保存到本地。

成功、跳过和取消的历史每小时清理，保留 7 天、最多 1000 条；本地清理或远端回执确认未完成时保留记录。失败及未完成任务不按年龄删除。停服备份应同时包含数据库和 `spool_path`。有待办文件时不要改换存储名称、URL、待上传目录或 ShardReel 的 `SR_STORAGE_ROOT`。

`/watch <来源> 0` 仍跟随默认存储及已启用的规则；修改默认值影响后续监听保存。`/copy` 仍是 Telegram 聊天间转发。

## TG收藏

```toml
# 需先启用 telegram.userbot.enable 并完成登录
[[storages]]
name = "TG收藏"
type = "telegram"
enable = true
chat_id = -1001234567890
topic_id = 0
```

目标为 Userbot 可写入的频道/超级群；非零 `topic_id` 必须是该论坛群中可用的话题。配置不会修改现有默认存储，需在保存设置中自行选择。普通链接保存、Bot 附件和默认存储监听（`/watch … 0`）均可使用；`/copy` 和直接指定目标的 `/watch` 保持原有复制行为。

频道/群消息先复用无来源复制，并尽力附加 `[转]` 原链接。复制请求仅在 Telegram 明确禁止转发时下载后重新上传，网络/权限错误不会触发此兜底。转发给 Bot 的附件若保留原频道及消息编号，会先核对可访问的原消息：整组成员、顺序、媒体、caption 和实体一致时直接复制原消息。来源缺失、不可访问或内容不一致时，使用收到的 Bot 附件下载上传；绝不把 Bot 私聊消息编号用于 Userbot 复制。有原频道信息时保留原链接，没有时不伪造来源。下载被拒绝时任务失败，不保证受保护内容都能保存。

媒体组按原顺序整体发送，保留 caption、文本实体和视频/音频属性。媒体组必须完整输入，不支持 `?single` 拆组收藏；解析媒体组失败时不会默默只收藏一个成员。频道/群媒体组发送前会复用现有的有限范围查询核对成员，发现选取不全或成员变化则报错，不自动补入成员绕过规则；此查询不能保证找出范围外的成员。Bot 私聊附件只能使用实际收到的成员。同一组的规则必须指向同一存储。没有目录、覆盖/跳过同名文件和文件浏览；文件名/目录规则不改变 Telegram 原消息，仍可用规则选择此存储。

仅上传兜底使用已有 `temp.base_path`（Docker 为 `/app/cache`），单文件上传后即清理，全部成员准备好才发布消息。任务详情显示复制、下载、上传、发送状态及收藏链接。取消停止后续工作，已确认发送的内容保留；删除任务记录不删除收藏。网络错误导致发送结果不明确时先检查目标，勿直接重复提交。任务与现有普通保存一样不支持重启后续传。

收藏目标不能同时作为监听来源：新监听会被拒绝；已有冲突监听会阻止启动并指出路由，先移除该监听再启用存储，防止循环。

### /collect 快捷收藏

- `/collect https://t.me/channel/123`：使用当前用户唯一可用的 TG收藏 存储中的聊天和 Topic。
- `/collect https://t.me/channel/123 -1001234567890`：该次改用此目标，不指定 Topic。
- `/collect https://t.me/channel/123 -1001234567890 2`：该次发送到 Topic 2；Topic 0 表示不指定。

目标必须使用数字聊天 ID，Topic 为独立的第三个参数。每次一个链接，媒体组自动整组提取；无需选择存储/目录。该指令不应用目录/命名/存储规则，不改变默认保存位置、收藏配置或监听。仍需先配置并授权 TG收藏；多个可用 TG收藏 配置时会提示先保留一个，避免猜测默认目标。
