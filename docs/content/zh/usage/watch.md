# 监听聊天

{{< hint warning >}}
该功能需开启 UserBot 集成.
{{< /hint >}}

监听指定聊天的媒体消息。`target=0`（或省略）时自动保存到默认存储；`target` 为其他频道/群 ID 时由 UserBot **无来源复制**（`DropAuthor`），并在消息开头加上可点击的 `[转]` 链接；源消息删除不影响已复制内容。

## 监听聊天

```
/watch <source_id> [target_id[:topicId]] [filter]
```

示例:

```
/watch -1002229835658
/watch -1002229835658 0 msgre:hello|world
/watch -1002229835658 -1003333444555
/watch -1002229835658 -1003333444555:12345
/watch -1002229835658 -1003333444555:12345 msgre:plana&(planb|planc)
```

## 列出监听

```
/lswatch
```

输出格式:

```
[id] <source名> -> <target名> [filter]
```

`target` 为 `0` 时显示为「本地」。有论坛话题时显示为 `目标群#话题名`。可用 `/lschannel`、`/lsgroup` 查看名称与 ID 对应关系。

## 列出论坛话题

```
/lstopic <group_id>
```

输出格式:

```
话题名 -> topicId
```

`topicId` 为论坛话题 ID（与 `t.me/c/<群>/<topicId>/...` 中一致），用于 `/watch` 的 `target:topicId` 语法。请用 `/lstopic` 获取。

## 列出频道 / 群组

```
/lschannel
/lsgroup
```

输出格式:

```
<名称> -> <id>
```

## 取消监听

```
/unwatch <id>
```

`id` 为 `/lswatch` 返回的自增主键。

成功停止后，该路由尚在等待的媒体组缓冲会被丢弃；即使定时器已经取出媒体组，本地保存任务在正式入队前也会再次检查路由。重新创建相同来源和目标的监听使用新路由身份，不继承旧缓冲。其他路由及 Topic 不受影响。

Userbot 在建立媒体事件时捕获当时的路由，随后进入每条消息约 5 秒的消抖及消费队列。等待期间更新媒体/caption 会保留首次事件的路由身份；停止并重建后，旧事件不会重新分配给新路由，同源存活路由仍可正常处理。接纳前再次检查捕获的路由是否有效。

这个边界按本实例建立事件的时刻判断，不按 Telegram 消息原发送时间截断。重连后才收到的消息按接收时的路由处理；新建监听若从相册中途开始收到成员，转发仍沿用整组取回契约，不会按监听建立时间拆分已选中的媒体组。

停止监听不会取消已经入队或执行中的保存任务，可通过任务列表单独取消。转发的等待队列按路由清理；工作槽位通过最终路由校验后视为开始执行，此后的转发可能在停止回复之后完成，不会因停止监听而截断媒体组。仅占用槽位但尚未通过校验的旧路由仍会被拒绝。本行为不提供跨实例停止保证；同一 Bot/Userbot 账号应保持单实例运行。

## 过滤器

### msgre

`msgre:` 后为关键词布尔表达式（`&` 与、`|` 或、`!` 非、`()` 分组），不区分大小写子串匹配。例如:

```
/watch -1002229835658 msgre:plana|planb
/watch -1002229835658 msgre:plana&(planb|planc)&(!spam)
```

## 转发说明

- 由 **UserBot 个人账号** 执行 `forwardMessages`（DropAuthor），Bot 仅负责管理命令
- 复制后编辑在开头加上 `[转]` 超链，点击可打开源消息；原样式随转发保留
- 相册命中后**整组**转发
- 源聊天需可读，目标聊天需有发消息权限

## 转发容量与顺序

监听转发采用独立的按需调度：最多 4 个工作槽位和 100 个等待项，单条消息或一个媒体组各算一个逻辑项。满队列时立即拒绝该项，记录日志及后台诊断计数，不额外重试或重启回放；本地保存继续原队列，`/copy` 使用自己的任务流程。

同目标聊天（包括其不同 Topic）按调度接纳顺序串行，整个转发及尽力而为的归因编辑结束后释放槽位。等待同一慢目标的内容不会占用其他工作槽位；但共享等待容量已满时，其他目标的新内容也可能被拒绝。普通 ID 与 Bot API ID 使用相同数值的调度键处理当前 Telegram 的不同 ID 格式，原始 ID 仍原样传给转发；不同 peer 类型恰好数值相同也会保守串行。

接纳顺序不是 Telegram 源消息的绝对顺序：相册分别在缓冲静默后进入调度，不同组或单条消息可能先后就绪。组内成员仍由原转发函数排序并整组取回，整组任一成员命中的过滤、代表消息选择、caption、富文本、来源链接及 Topic 契约不变。与 `/copy` 或手动客户端之间不提供跨流程串行保证。

`/unwatch` 成功后丢弃本路由缓冲和转发等待项，开始前再次检查原路由身份。已开始的转发、本地保存任务和其他路由不因此取消；同目标的新任务仍需等待已开始的旧转发完成。服务 context 取消会清掉转发等待项并结束工作线程；这些观察及队列不持久化。

后台诊断展示转发等待/占用/上限、接纳/开始/成功/失败、拒绝及丢弃计数，仅覆盖本调度器，不含前置消抖、来源 channel 或媒体组缓冲，亦不是整个监听链路的内存上限。槽位包含最终校验阶段；成功只表示转发函数成功返回，不能证明取组完整或归因编辑成功。

## 媒体组验收清单

以下为升级后的人工验收模板，不是当前版本的实测结果。使用独立测试内容、源聊天与目标聊天，优先使用专用 Bot 和 UserBot 会话，并按实际启用场景选择项目；单用户部署无需额外准备第二位用户，多用户隔离或多话题验收才需要相应用户和话题。记录测试版本、源消息 ID、目标消息 ID、预期与实际结果，已有实测证据应写入对应版本的验收报告。

- [ ] **普通收件与静默保存**：发送照片、视频相册及单条媒体，核对文件数量、caption 命名和保存位置；启用多用户时补查两位用户同时发送、各用户内容不混组。
- [ ] **重叠相册**：同一源聊天连续发送两组相册；监听保存和转发均保持组边界；连续无交错场景核对顺序，交错场景同时记录每组就绪与调度接纳顺序，不把接纳顺序当作源消息绝对顺序。
- [ ] **整组过滤**：只有一条 caption 命中 `msgre` 时，转发完整相册；整组无命中时不转发，也不保存。
- [ ] **默认存储与相册规则**：`target=0` 的保存结果符合现有目录、命名及相册规则，每个文件只保存一次。
- [ ] **多目标与话题**：同一源分别监听到两个目标，以及同一论坛群的两个话题；每个目标各收到完整一组，话题之间不串组。
- [ ] **停止与重建监听**：在媒体组缓冲等待期间停止一条路由，核对其未接纳内容不再保存或转发、其他路由正常；重建同一来源和目标后不继承旧缓冲。已接纳本地保存和已通过最终校验的转发可继续完成；新增等待队列及开始前已取出的旧项都不得越过停止边界。
- [ ] **归因与富文本**：使用带粗体、链接和 emoji 的 caption，检查 `[转]` 指向正确源消息，文字与原样式保持。
- [ ] **批量复制与取消**：通过 `/copy` 复制命中的相册并取消另一项复制；检查整组完整性、最终状态、取消按钮清理和再次启动复制的能力。
- [ ] **限流与恢复**：通过可控模拟或自然发生的 `FLOOD_WAIT`，验证等待提示、取消响应和最终状态；未实际覆盖限流时将此项保持为未验收。

自动回归不能替代适用场景的真实环境检查。未覆盖的场景保留为未验收或不适用；已有实测按版本报告记录，不因本模板未勾选而重复执行。

媒体组取回使用代表消息前后各最多 49 个 ID（总计最多 99 个），单个正常 peer 查询在原 100-ID 分块预算内；可覆盖窗口内稀疏、交错成员，按 ID 排序去重，不混入其他 group。取消、超时或 FLOOD_WAIT 不继续尝试 peer 别名。查询结果仍是有限窗口中的尽力选取，无法知道预期成员总数；非空、一成员或超过窗口的情况不自动标为已知降级，也不证明整组完整。
