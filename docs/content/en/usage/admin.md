# Web administration

The optional console uses the fixed username `admin`. It is disabled by default and independent of the Bearer-token API.

```toml
[admin]
enable = true
host = "127.0.0.1"
port = 8081
password = "replace-with-your-long-password"
session_ttl = "12h"
secure_cookie = false
```

Passwords must contain 12–1024 bytes. Restart manually and visit `http://127.0.0.1:8081/admin/`. The console starts after Telegram initialization; use container logs for earlier startup failures. Invalid console credentials or listener settings prevent the console from starting without stopping the Bot; a configuration decoding error still prevents application initialization.

Prefer a hash: run `saveany-bot admin-password`, enter and confirm the password, and replace `password` with the printed `password_hash` line. Only the bounded Argon2id format generated by this command is supported. The command does not start the Bot or read configuration. Secret-file automation can use `saveany-bot admin-password --stdin < /path/to/password-file`; it removes one trailing newline and preserves spaces. Do not put passwords in command-line arguments.

The Docker default entrypoint starts the Bot and does not forward CLI arguments. To generate a hash, use `docker run --rm -it --entrypoint /app/saveany-bot <your-image> admin-password`, or execute `/app/saveany-bot admin-password` inside a running container.

All fields support `SAVEANY_ADMIN_*` environment variables, including `SAVEANY_ADMIN_PASSWORD_HASH`. Exactly one of `password` and `password_hash` is required. Session lifetime must be between `5m` and `24h`, defaulting to `12h`.

The repository Compose uses host networking. For a custom bridge network, listen on `0.0.0.0` inside the container and publish to host loopback, such as `127.0.0.1:8081:8081`. For LAN use, configure the listener explicitly and use an HTTPS reverse proxy with `secure_cookie=true` and the original Host preserved. Arbitrary forwarded headers are not trusted. HTTPS-only cookies cannot maintain an HTTP login. Existing API tokens cannot log into the console, and console cookies cannot authenticate the original API. Deploy a fixed version or image digest containing the console and verify the running commit. The `latest` tag changes with releases and does not confirm that a feature has been updated.

The console provides overview, active queue tasks, tracked web/API results, task submission/cancellation, storage capabilities, local directory browsing with Range downloads, and ShardReel browsing/downloads. When ShardReel is configured, the overview shows unfinished files, failed files and reserved space against the outbox limit. Reserved space includes downloads and files awaiting cleanup, rather than measured directory size. Watch routes can be created/stopped and changed scalar save preferences can be edited. Directory shortcuts and save rules can be added, edited and deleted on the preferences page. Old events cannot rebind when a route is stopped and recreated. Forwarding outside the queue is not represented as a cancellable task.

Overview and task pages refresh about three seconds after a load completes while tasks are active, or fifteen seconds when idle. Activity detection includes tasks hidden by search, filters or pagination. Hidden tabs, open task details and focused table controls pause automatic refresh; manual refresh remains available.

Recent terminal observations cover Bot, web and API queue tasks, with submission sources and available progress/counts. Ordinary queue observations are in memory and reset at restart. ShardReel upload tasks persist in SQLite with per-file progress and cleanup state; complete staged files resume after restart. Clean terminal upload history is retained for seven days, at most 1000 tasks. Web/API history retains up to 1000 terminal entries for about 24 hours, evicting the least recently updated first; Bot queue observations have an independent 1000-entry, 24-hour budget. The console merges them by ID, so these budgets are not a total row limit. Queued, executing and cancellation-cleanup tasks are not evicted by history limits. Existing completion and hook decisions remain unchanged; unavailable copy counts are not fabricated. Diagnostics also show watch backlog/drop counters, local available disk space and Telegram initialization. Initialized is not a live connectivity check; watch counters reset at startup and are not file outcomes. Diagnostics use a configuration whitelist and up to 100 in-memory management operations, not arbitrary log/config files. Known configuration/database/session files and sidecars are protected from downloads, including aliases. Keep private deployment files and other deployment files outside local save roots: administrators may access other files inside those roots.

Sessions are bounded to 16; new sessions evict the earliest-expiring entry when necessary. Logout and restart invalidate sessions. Each client address can make five login attempts per minute; clients behind a reverse proxy may share that quota. Browser writes require same-origin Origin and a session-bound CSRF token. Cookies are HttpOnly/SameSite=Strict; the browser stores only language preferences outside cookies.

Chinese/English UI assets are embedded in the Go binary. No CDN, Node runtime, or additional frontend container is required.

Task details show link selection results by submitted position. Creation shows a separate dialog for failed or duplicate inputs, known album fallback or omitted metadata. Album lookup errors and empty results indicate that only the original message was considered; the warning remains when that message is already selected or unsupported, preserving existing ready/duplicate/failed statuses. All-failed requests retain the input and do not create a task. At most the first 100 results are shown, with an omitted count. Selection means inclusion in a task, not download completion or proof of a complete album. The Bot sends a separate bounded note for failed, duplicate or partly selected links, preserving the original selection keyboard and captions; Bot positions refer to matched Telegram links and each note shows at most ten entries.

Scan diagnostics report completed history/search pages, successes, failures, timeout/cancellation subsets, and last/maximum page durations since startup. They retain no per-request content and measure pages rather than whole tasks.

Watch forwarding uses a separate scheduler and is excluded from task history. Diagnostics show up to four occupied slots and 100 waiting messages/albums, results, rejections and discards. Slots include final route validation, without automatic retries; success does not prove album completeness or attribution edits. The same target chat runs in admission order with original IDs and Topics preserved. Upstream media buffers and local-save/copy queues are outside this capacity. See the watch documentation for stop boundaries. Copy task details retain bounded logical-item counts after execution; old records do not fabricate counts, and ordinary-failure status/hooks remain unchanged.

The new-task page also provides a history-copy wizard for a configured user, one source, one managed target chat, optional Topic and a count of 1–5000 logical items. Target 0 is forbidden. Copies share the Bot ownership guard, core queue, cancellation and bounded task history, without Telegram progress messages. Admitted tasks retain service lifetime when a browser request ends. Lifecycle status/hooks use the worker’s terminal decision; a separate label distinguishes all successful, partial failure/interruption, no successful items and no matches. Confirmed sends are never retried automatically.

Management requires login, same-origin requests and session CSRF tokens. Preparation is limited to two concurrent operations with a 25-second request budget. Topic pagination rejects repeated cursors and has a finite page budget. Failed raw RPC details stay in server logs. Stops use the same admission gate and clear waiting work while allowing started forwards/accepted saves to finish. Only changed scalar preferences are written; changing storage clears its old default directory. Directory shortcuts and rules support create, edit and delete without moving or removing saved files. Deleting a default shortcut or changing its storage resets the default directory to the storage root, preserving default storage. Directory choices are filtered to the selected storage. Rules offer built-in file-type patterns, message regex and album/single-media conditions, with a concrete destination or the storage chosen for that save. Adding a rule does not enable rules; edits retain IDs and do not reorganize old files. Save pending scalar preferences before managing lists. Synthetic filename preview supports literal text and .msgid/.msgtags/.msggen/.msgraw/.msgdate/.origname/.chatid fields, without loops or formatting functions. Only complete staged ShardReel files resume after restart; Telegram downloads and forwarding are not replayed.

Interrupted counts mean no success confirmation; a send may already have reached the server, so it must not be retried automatically. Reselecting the current storage preserves its default directory. Switching storage clears the old directory unless a new one is explicitly selected.

Preference updates validate the final silent/storage/directory combination in one transaction. Invalid combinations roll back the entire patch. Reselecting the same storage preserves its directory; switching storage clears the old directory unless a directory owned by that user and storage is explicitly selected.

The source dropdown selects one chat and searches names/IDs directly in its input. Sources and targets share a durable local chat list, including normal and archived dialogs; either adjacent refresh button synchronizes that list. Target dropdowns show creator/admin memberships of the current Userbot account; management identity is rechecked for new watches and copies, without promising sending permissions. Saving to configured storage remains a separate watch destination. Watches process photos/videos/files, not text-only messages. Source and target must differ.

Topic options load automatically after choosing a forum target. “No Topic” is the first/default option; switching targets clears old selection and stale responses are ignored. Destination and include-any/include-all choices use radio controls. Basic filters use literal, case-insensitive include/exclude keywords, one per line. They match text/captions, not filenames, with the existing 16-term/256-UTF-8-byte limits; English double quotes are unsupported in basic keywords. An album matches when any member satisfies the full condition; exclusion is per member, not a group-wide veto. The no-network sample preview is available; advanced expression preview remains on the preferences page.

New-task tabs choose file saving or history copying and preserve inputs when switching. Optional filters start collapsed with a summary of the actual include/exclude words. Invalid filters open with an error. Sample testing is optional; changing conditions or sample text clears the old result, and stale responses are ignored. Save watches show the current default storage/directory, any save-rule warning and a link to preferences. A missing default storage blocks save-watch creation.

Confirmations show source, target, Topic, filter and copy count, or the default save destination. Each submission creates one watch route. Unconfirmed results require checking the task/watch list before retrying; no send is retried automatically. Chat query failures and rejected submissions preserve the current form. A browser reload starts a new form. Accepted copy tasks keep running when the browser closes.

Task lists show available result counts and distinguish messages/albums from files. Completed tasks with known results short of full success are labeled “Execution ended”, as are completed copies without success confirmation; inspect success, failure, cancellation, interruption and unattempted counts. Unsaved file counts include failures and conflict-policy skips; details show each available count. Lifecycle status/hooks remain unchanged and missing counts are not fabricated.

Page loads, browser reloads and target changes read SQLite snapshots without Telegram RPCs. Use the adjacent refresh buttons to synchronize; missing snapshots prompt a manual refresh and saved lists show the last-sync time. Snapshots are scoped to the Userbot account, with Topics keyed by target chat. Only display IDs/titles/state are stored, not credentials or access hashes. Full successful scans replace snapshots atomically; failures preserve old data and selections. Chat refreshes invalidate obsolete Topic caches. Syncs are serialized and retain the 25-second request budget, at most 100 chat pages/10000 entries and 1000 Topics. Snapshots survive restarts, using an additive cache-table migration. Cached roles never replace live submission checks. Local saving hides target and Topic fields; only forums display Topic fields. Topic refreshes preserve a still-valid selection and the first/default option remains “No Topic”.

### Task cancellation and record deletion

Each row shows only Details + Cancel or Details + Delete. Both execute immediately without a confirmation dialog. Queued, downloading, uploading and automatic-retry waits are active. Cancellation cleanup disables the action until execution ends. Cancellation does not undo saved files or sent messages.

Deletion removes task history, file details and retained upload payloads only. Saved local/ShardReel files, Telegram messages and watch routes remain. For ShardReel it stops retries, confirms remote cancellation or completion, cleans staged files and acknowledges receipts before removing records. Incomplete cleanup retains the record with an error; try deleting again shortly. Executing tasks and pending result delivery block deletion. Deletion is irreversible. Success removes the row and falls back to a valid page if necessary.

### Combined filters and copy progress

Copy and watch support simple keywords or a combined expression such as `msgre:dance&(king8|k8)`. Existing text previews use the same parser; invalid expressions cannot create a task. Copy tasks show search matches, actual copying progress and success/failure results, with no search percentage. Titles contain source, full filter, target and optional `Topic:Name(id)`; omit the suffix without a topic. Cancellation and history-deletion boundaries are unchanged.
