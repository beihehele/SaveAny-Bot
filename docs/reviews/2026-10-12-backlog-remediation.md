## 本轮处理

### 共享入口的路由归属

媒体事件在进入 Userbot 消抖前捕获路由值快照；消费端使用捕获的接收者，不再按来源重新查询当前路由。重复消息刷新媒体/caption 时保留首次接收者，第一次入缓冲时复制切片，避免调用者随后修改。旧路由删除后的事件由原有接纳门禁拒绝；同源存活路由继续收件，新建路由处理后续事件。没有清空共享入口或取消共享客户端。

生产入口和消费者调用者已核对：发送媒体事件的生产调用者是 `client/user/watch.go`，没有其他生产代码依赖不带路由的事件。无快照、外来源、无媒体/上下文或已取消的事件不会接纳。消费逻辑提取为可隔离验证的函数，真实监听循环调用该函数；源聊天预过滤仍保留，正常事件的来源查询由消费端前移到事件建立端，不增加 Telegram RPC。

这个边界不是按 Telegram 原发送时间截断，也不是相册第一成员永久绑定某代路由。重连后第一次接收的消息使用当时路由；新监听从相册中途开始接收成员时，转发仍沿用原整组查询契约。没有修改取组窗口、转发方法、DropAuthor、caption/富文本、来源链接、Topic、成员排序、命名、500ms copy 节奏或已接纳任务/hooks。

回归核对快照所有权、刷新后保留最新媒体/文本、旧定时器、新事件重用 key、两个配置用户和同源多路由。实际数据库及应用队列的隔离子进程覆盖旧单文件/两成员相册等待后停止并重建、存活 Topic 收到完整两成员组、重建路由仅接收新事件、单文件/相册正式入队、caption 不被改写、未知接收者与外来源拒绝。采用长测试定时器后确定性取组，没有固定 sleep 或 Telegram 会话。

### 偏好更新复活已删除关联

继续核实发现 `UpdateUser` 会保存预加载的关联快照，修改静默、默认保存或命名时可能重新插入已删除的监听、目录及规则。新回归在原实现上确实恢复三类记录。现只保存用户标量字段，显式省略 associations；关联项继续由原专用管理方法处理，没有改变配置同步用户、schema 或关联 CRUD。

已核对 `UpdateUser` 全部生产调用者均修改用户标量字段。测试核对旧快照不会恢复三类关联，设置值和 false/空字符串清空值都能保存；现有配置同步、保存偏好、存储引用和合成备份恢复回归一起核对。此修复不宣称已经实现任意偏好字段的并发合并。

### copy 最后边界的取消传递

复核 `copyfwd.Execute` 确认，取消若发生在最后一次 RPC 或最后一次进度回调，原循环可能没有下一次迭代检查 context，最终返回 nil。隔离完整执行回归在原行为下复现四处：末次 RPC、已确认转发后取消、末次进度、空扫描最终反馈。普通转发失败与成功对照在原行为下通过。

增加扫描反馈结束及每次转发/反馈结束的 context 检查，保留取消原因供原 worker 选择取消结果/hooks。已经确认转发的数量保持成功计数，不撤回已发送内容，不自动重试，结束回执仍只调用一次，用户复制占用仍在 defer 中释放。执行体接收客户端 getter 便于用真正的消息扫描/转发 RPC mock 验证；公开 Execute 使用原 `user.GetCtx`，getter 求值仍在清理 defer 建立后。

没有改变普通 RPC 失败累计 failed 后仍完成循环的原有政策。末次取消修复与“部分/全部普通失败应选择何种终态”是两个问题；后者仍在以下待办中。新测试夹具首次有 Invoker/Self 类型错误，修正后才复现四个业务断言；原编译日志保留，不把夹具错误算作产品缺陷。

### copy 后台逻辑项结果计数（后续批次）

`copyfwd.Task` 实现 `taskresult.Provider`，以互斥保护固定大小的汇总值，不保留逐消息的 ID、caption、错误列表或成员数组。总数只在完整扫描成功后确定，按实际选中的单条消息/整组计算，与请求 count、媒体文件数区分；扫描错误不发布部分列表。执行前先清空汇总，每次转发调用前后记录正在处理与结果，不增加 RPC、重试或改变 500ms 节奏。

成功调用保持 succeeded，即使随后来源链接编辑或进度反馈期间取消；普通错误保持 failed，不因同时取消而改写。取消形态错误依据父 context 区分 cancelled/interrupted；尚未开始的项保持 pending，便于说明取消后未处理内容。Bot 原 copied/failed 回执不变，取消尝试/内部中断仍归入其 failed；worker/hooks 和普通失败后继续执行的完成政策保持原样。

结果通过原 worker 终态事件和有界 Bot 历史进入后台，不新增存储表或重启回放。任务详情提供中英文单位及可读计数，说明“已完成”是流程结束、成功不证明整组完整或归因编辑成功；历史旧记录不补造计数，保存任务继续原显示。监听的队列外转发仍不冒充 copy 任务历史。

隔离子进程用实际扫描、取组、转发与 worker，mock Telegram 传输，核对两成员媒体组加单条消息总数为 2、成员顺序/Topic/DropAuthor、11 种成功/普通失败/取消/内部中断/空扫描/扫描失败/客户端不可用情形，以及并发读取、终态事件和历史汇总一致。原最后取消的六个回归亦核对汇总。独立 HTTP 测试验证后台保留完成/取消政策和逻辑项，不误填文件进度；合成浏览器核对中英文、旧记录及保存任务。

首次新夹具错误返回了 RPC 未请求的已缓存代表消息，导致重复成员断言，修正 mock 为仅返回请求 ID 后通过；该现象不算生产取组缺陷。overlay 负对照只改变完整扫描后汇总发布，用于验证结果接线；首次命令参数解析错误记录单独保留，不能算业务负对照。

全量检查时旧超时测试在并行编译/竞态负载下曾让“快速成功的第一页”先超过 80ms，导致期待第二页的调用数断言失败，部分结果仍没有泄漏，共享和父 context 均未取消。测试页面预算改为 1 秒，并同步给原 30ms 的连续恢复夹具留出余量；仍等待实际 context deadline，不修改生产扫描配置、不减少页数/丢弃部分结果/同客户端恢复断言，也不使用固定 sleep 制造超时。初次全量日志保留，最终源码另行冻结检查。

### 监听转发有界调度（后续批次）

原单条转发和相册 flush 都直接启动 goroutine，来源 channel 容量 100 不限制 RPC 并发；同目标多条/跨组亦无串行保证。现共用独立调度器，最多 4 个工作槽位、100 个等待逻辑项，队满立即拒绝并记录日志/计数，不等待额度，不额外重试或重启回放。队列仅保留路由值和代表消息 ID，不保存源文件、caption 或逐成员数组；前置消抖/来源 channel/媒体组缓冲仍有自己的范围，不把本调度额度冒充整条监听链路内存上限。

同目标聊天含不同 Topic 按接纳顺序串行，槽位覆盖取消息/取组/转发/尽力而为的归因编辑；等待同一慢目标的项不占额外槽位，工作线程可跳过它们处理其他目标。共享等待容量满时所有新项仍可能被拒绝。历史普通 ID 与 Bot API ID 取相同 plain 数值作为保守互斥键，原 ID 传给原转发函数不变；不同 peer 类型恰好同数值也可能串行，不为调度引入解析 RPC 或修改已有路由。

停止边界明确区分等待与开始：同一个路由接纳门禁串行 enqueue、停止及最终开始校验。成功删除清理该路由媒体组缓冲和转发等待项；已取出的槽位若未通过校验也会被拒绝。通过最终路由校验标记 Started 后释放门禁再执行 RPC，已经开始的转发不因 `/unwatch` 截断；本地保存原已入队/执行生命周期、其他路由、重建身份保护及共享客户端保持。队列 mutex 不覆盖门禁查询或 RPC，锁顺序为 route gate -> queue；worker 取项后释放 queue 锁才检查 gate，避免停止/入队锁反转。共享服务 context 结束丢弃等待并结束所有工作线程，不主动取消共享客户端。

相册缓冲保留首次代表消息、任意成员命中过滤、计时器所有权和原整组取回。排序、DropAuthor、Topic、caption、富文本与 `[转]` 来源链接仍由原 `user.ForwardMessage` 执行。组/单条的就绪接纳顺序不等于 Telegram 源消息绝对顺序，亦不对 `/copy` 或手动客户端提供跨流程串行保证。后台任务历史仍不纳入监听转发；诊断新增只读、有界的槽位/等待/上限/结果/拒绝/丢弃计数，区分父取消与内部中断。开始前校验错误计入 failed；成功只表示原函数成功返回，不证明整组完整或归因编辑成功。

首轮现有回归、调度单测和真实函数管线回归通过。阻塞传输的确定性用例核对上限、50 个并发满队列拒绝、跨 Topic 与历史 ID 别名顺序、慢目标与其他目标、请求 context 与服务 lifetime、停止/重建、已经取出的开始前旧项、共享服务关闭、普通错误/内部超时/最终数据库错误释放槽位及不重试。隔离数据库/真实入口、相册 flush、正式本地队列及原 Telegram 转发函数（仅 transport mock）核对：满队列不堵本地保存、外国用户停止不清旧项、停止保留阻塞中的真实转发、反序到达两成员整组过滤、RPC ID 排序/Topic/DropAuthor/来源链接/粗体/emoji/原 caption 不变，以及 queued 本地保存未被取消。新增功能暂未真实 Telegram 验收，最终全量/竞态/WSL结果见后续核对记录。
