# SaveAny Bot 分批实施、整体复查与发布评估

本轮从 `dev` 的 `402003e` 开始，在 2026-10-07 至 10-08 完成核实、分批修复、专项复查及整体检查。整体范围包含 `origin/dev` 的 `6ae4475` 之后此前 19 个提交和本轮提交；没有合并 main，没有推送、打 tag 或部署。用户已有的 `docs/superpowers/specs/2026-07-26-telegram-netdisk-feasibility.md` 未修改或纳入提交。

整体 review 后又实施了流式退出、媒体定时器和 Aria2 入队补偿修复，随后补齐监听观测、只读文件摘要与 API transfer 的可选结果策略。最新源码为 `509e9ea`，验证范围见文末第三批记录；`56a5bb9` 的两批验证和此前 `75e9b42`（gotd 安全补丁）、`9493a33`（Playwright）的验证保留为历史记录。质量工作流基准仍为 `535188f`。本报告各历史批次的“未改动”范围仅描述当时提交，不能用于判断最新源码。

结论：已实施批次通过本地代码复查及相应自动回归，可以作为待合入候选逐批审阅；整个项目暂不满足正式发布条件。Windows 全项目 race 已通过，Windows/Linux 默认源码扫描无可达漏洞，但仍有模块/包级提示。真实 Telegram、目标 Linux/容器、远端 CI 与部署副本恢复的验收尚缺。不能把“修复代码通过检查”解释为“全部待办关闭”或“部署已验证”。

## 续批复查与自更新方案核实

续批按照 VM 调度与取消 → 来源组替换 → 路由取消边界三个本地提交推进，每批专项检查通过后才继续。整体复查另外修正了 Windows 临时目录短路径别名导致的重复注册问题，未改媒体组转发路径，也未改变原生解析器的必需接口。

从架构角度，同一 VM 的 JS 调用、值转换和结果导出现在归同一个执行门协调；取消中断协程先退出，再清除中断并释放执行门，避免迟到中断污染后续调用。注册表以来源组表达所有权，不要求 Parser 接口值可比较；替换只撤销旧组的发布能力，活动调用仍能完成，没有关闭仍被发送的解析 channel。来源锁协调程序内安装与加载，不能承诺程序外进程同时编辑文件时的事务一致性，也不提供 JS 内存配额或不可信脚本沙箱。

从产品角度，覆盖插件后新任务会使用新版；失败安装保留原插件，已经开始的任务可完成，等待中的旧调用返回替换错误。默认期限防止坏脚本永久占住匹配，但不是整个程序的总期限：一个请求可依次检查多个脚本，API 的 30 秒预处理期限仍受 Playwright/Telegram 原生调用限制。升级前应确认现有插件的解析时长；默认期限暂未开放配置。

自更新上一批只做候选核实，本批已实施项目内的窄范围适配器并移除旧依赖，未执行真实程序替换。候选 `github.com/creativeprojects/go-selfupdate v1.6.0` 的[官方源码](https://github.com/creativeprojects/go-selfupdate/blob/v1.6.0/validate.go)仍直接导入旧 OpenPGP，[模块声明](https://github.com/creativeprojects/go-selfupdate/blob/v1.6.0/go.mod)还要求 Go 1.25.12 并引入其他托管服务依赖，因此没有采用直接换库方案。

两个更新契约已修复：CLI 使用一次检测的不可变资产快照，不再在替换时再次查询 latest；Bot 按钮绑定资产 ID，点击时复查 ID、同主版本及严格递增的版本策略，再使用该快照下载。旧的无资产 ID 按钮拒绝更新，要求重新 `/update`。同进程只允许一项替换，成功后再次更新要求先重启。

适配器按 [GitHub 官方 Release API](https://docs.github.com/en/rest/releases/releases?apiVersion=2022-11-28) 分页查询，选择匹配平台的最高稳定语义版本；下载使用 [asset ID 端点及 digest](https://docs.github.com/en/rest/releases/assets?apiVersion=2022-11-28)，不把展示 URL 作为下载来源。资产名和 zip/tar.gz 内的程序名与[当前发布 action 源码](https://github.com/wangyoucao577/go-release-action/blob/v1/release.sh)核对，并在工作流启用 `.sha256` 输出。资产、解压 tar 总量和单程序各限 512 MiB；校验完整压缩数据后才解压，Go 构建信息再核对程序模块、OS/架构和默认构建标签。SHA-256 来源是 GitHub metadata 或同一发布的校验文件，完整性校验仍信任发布者，不等于独立签名认证。

提交前取消不改变原程序；提交开始后完成替换或回滚，成功保留并报告 `.saveany-update-old-*`。普通失败保留原文件，模拟的回滚失败仍保留旧文件并给出恢复路径。该备份不能替代配置、数据库与会话备份，也不保证断电时两个 rename 之间没有中间状态。当前适配器限公开仓库和本项目发布资产，没有新增私有仓库凭据或 Enterprise 支持。直连 fork 的公开发布查询在本机因 TLS 失败未取得有效结果，已记录为真实下载/发布验收缺口；本批依靠官方 API/action 源码、HTTP 夹具和临时文件验证。

## Playwright 续批复核、架构与产品评估

复核确认了三个可直接修复的问题：安装错误保存在请求局部变量，但 `sync.Once` 在失败后也不再执行，下一请求会丢失安装错误并尝试启动；安装协调只属于单个 VM，而所有 VM 写同一个 `./playwright`；每次 Install/Run 传入 Logger 都会赋值上游包级 logger，并发插件可产生共享写入。本批使用进程级可取消的安装执行门，只缓存成功结果，并停止在请求中修改上游全局 logger。失败安装保留上下文错误供调用者判断，下一请求可以重试；不自动删除或重装现有驱动目录，部分下载或损坏的目录仍可能需要人工处理。

架构上，每个请求仍独立拥有驱动、浏览器和页面，Goja 值转换始终在原 VM 执行门内进行。取消后停止后续阶段；浏览器启动最多 30 秒，导航最多 60 秒，均取当前请求的更短剩余期限。所有已取得资源按浏览器 → 驱动的顺序释放，关闭错误记录日志并保留在返回错误中，浏览器关闭失败仍尝试停止驱动。没有引入在调用者返回后继续操作 VM 的后台协程。阻塞原生调用的回归专门确认：调用未返回时 VM 所有权不被提前释放，等待者可取消，调用和清理结束后清除中断并继续复用 VM。

本批仍不是完整原生取消方案。核对 v0.5700.1 的[安装/启动源码](https://github.com/playwright-community/playwright-go/blob/v0.5700.1/run.go)确认：安装不接收 context，包含默认 HTTP 客户端下载及普通 `exec.Cmd.Run`；启动还需要驱动版本检查及初始化握手。核对[传输停止源码](https://github.com/playwright-community/playwright-go/blob/v0.5700.1/transport.go)确认：Stop 关闭 stdin 后等待进程退出，没有应用层强制截止。因此启动/导航的驱动超时、阶段取消与 VM Interrupt 不能保证安装、页面读取和关闭在请求期限内返回；本批没有并发 Stop 或放弃后台 goroutine 来冒充完整取消。

产品上，`playwright.get(url)` 保留成功返回 HTML 字符串、失败返回 `{error}` 的接口；关闭失败现在也返回错误对象。文档原称“非 200 失败”与原代码不符，本批纠正说明，继续允许正常导航及重定向，只拒绝最终响应状态码大于等于 400，未收紧状态码行为。首次成功安装后其他插件复用安装结果，失败可以重试；取消安装等待不会影响正在安装的请求。浏览器下载仍可能超过初始化/解析的默认期限，部署应提前准备匹配版本，不在 `canHandle` 内执行浏览器请求。

验证使用模拟驱动和阻塞阶段控制，未触碰工作区的真实 Playwright 安装。当前工作目录没有所需驱动，用户缓存中的浏览器也不能据此认定匹配 1.57.0，未擅自下载或启动。Windows/Linux 默认、micro/pico 构建，以及 no_playwright 的解析/API 回归均通过；进程树、真实浏览器与目标容器运行依旧待验收。

下一步原生硬期限方案需要可独立停止并回收的工作进程、安装暂存/失败恢复、输出边界和 Windows/Linux 子进程清理设计，并在隔离浏览器环境验证。A06/A08 因此保留部分完成；A14 的文件级部分失败摘要、A19 的积压观测等仍按原待办独立评估，不借此批修改媒体组算法或现有 IgnoreErrors 语义。

### A19 监听观测

在成功登录的服务 context 下启动一个 30 秒采样的观察协程，服务取消时记录最后一次快照并退出。常规快照使用 Debug；区间新增丢弃使用 Warn，并保留每次通道满载的即时 Warn。新增字段：

| 字段 | 含义 |
| --- | --- |
| `pending` | 正在等待去抖的唯一 chat/message 键数，不是媒体组数。 |
| `buffered` / `capacity` | 采样时监听通道的占用/容量，容量仍为 100。 |
| `enqueued_total` | 此进程成功提交到监听通道的事件数，不等于成功保存/转发数。 |
| `dropped_total` | 此进程因通道满载而丢弃的事件数。 |
| `dropped_since_last` | 两次观察之间的新增丢弃数，仅出现在丢弃摘要中。 |

累计值在重启后归零。通道长度、去抖 map 和原子计数分别采样，快照不是强一致账本；瞬时峰值可能发生在两次采样之间。原始消息接收/重复更新不属于通道提交计数。若要观察常规积压需启用 Debug 日志；未增加监控端点、自动重试、扩容、持久化或丢弃补偿，也没有改变相册聚合键、去抖时长、过滤、caption、转发/topic 或消费顺序。

### A25 Aria2 排队取消：问题已复现，按使用范围实施

通过临时 Go overlay 加入 mock RPC 探针，成功创建任务后主动取消、关闭并排空队列，实际 RPC 序列仅含 `aria2.addUri`，没有停止该 GID。探针未写入仓库，也未访问真实 Aria2/Telegram。原因是 `pkg/queue.Get` 跳过已取消的排队任务，而清理只位于 `aria2dl.Execute`；API/Bot 的运行期清理均不能覆盖没有进入 Execute 的任务。排队停止期间的 service context 取消也需同样覆盖。

交叉核对 Bot shortcut 另发现：`CreateAndAddAria2TaskWithEdit` 在 AddURI 成功但 core.AddTask 失败后只反馈错误，没有补偿 GID。因此前一批已完成的入队前清理只覆盖 API，不能扩写成 Bot/API 均已覆盖。此问题列入启用 Aria2 时的同批修复范围；不通过通用队列修改来掩盖创建方尚未交接的责任。

仓库只有配置示例，不能据此确认生产使用状态。已经询问是否使用 `/aria2dl` 或 API 创建 Aria2 任务；未获部署事实前保留“使用状态未知”，本批不改通用队列和 Aria2 取消路径。确认启用时按以下方案单独实施：

1. 为已成功创建的 GID 明确“等待队列接收 → 排队 → worker 接管 → 完成/取消”归属；队列跳过或关停排队任务时，应在锁外交还清理责任，并对清理有总期限和完成等待。
2. 取消与 worker 接管必须在同一协调机制下决定归属，清理至多一次；不要用一次 `IsTaskExecuting` 查询加后台回调充当原子交接，也不要在每个任务的 Done context 取消上无条件删除 GID。
3. 重用已知 GID 的子下载清理规则：先停止活动任务，子下载清理失败保留父元数据和具体 GID；记录服务日志，保留已下载文件。统一运行期和未执行任务的规则前，核实 Bot/API 两种创建路径。
4. mock 覆盖排队取消、父 context 取消、关停队列、取消与 Get 竞争、Execute 前 hook 期间取消、正常完成不二次删除、失败恢复、子 GID 和清理超时；再做真实 RPC 验收。

RPC 结果丢失、未取得 GID 是另一边界，不能根据 URL 猜测并删除外部下载。请求前指定可恢复标识的方案仍需独立验证服务端支持、冲突、幂等/重试及所有权，不与本次已知 GID 的排队取消修复混为一项。不承诺跨进程恢复。

### A14 部分失败：只读摘要已实施，终态契约分阶段适配

临时 overlay 探针复现：batch 构造时传入 `IgnoreErrors=true`，单文件存储失败仍返回错误，且 `failed` map 为空；transfer 使用同一参数，一项读取失败、另一项保存成功，最终返回 nil、上传字节为成功文件的大小、`FailedFiles` 含失败文件。源码核对确认：core 对 nil 执行 TaskSuccess，API 对 nil 的 PhaseDone 标为 completed；transfer 的 Telegram 展示会列出失败文件，但总体仍显示成功。API 的 tgfiles/transfer 和 Bot shortcut 均存在启用 IgnoreErrors 的调用，因此不是只影响未使用的可选字段。

完整终态契约的目标如下。摘要和 API transfer 的可选适配已实施；其他任务/展示及继续策略仍按阶段推进，不将本表视为所有类型的现有行为：

| 情形 | 推荐结果 | 兼容处理 |
| --- | --- | --- |
| 全部已提交元素成功 | 完全成功 | 保留既有成功终态/hook。 |
| 按明确的冲突策略跳过 | 单独记 skipped | 不计作错误；预处理时已排除的文件也需明确统计来源，不能直接用任务元素数当原始总数。 |
| 普通失败且允许继续 | 继续剩余元素，最终报告部分失败；全部失败时报告失败 | IgnoreErrors 应表达是否继续，而不是掩盖结果；现有 transfer 客户端/hook 可能依赖 nil，不能无版本/适配直接改行为。 |
| 普通失败且不允许继续 | 停止后续工作，记录已成功、失败及未完成元素 | 已保存的文件不自动回滚；内部 errgroup 取消不能冒充用户主动取消。 |
| 用户/服务取消 | cancelled，保留取消前结果摘要 | 不吞取消错误，不触发 TaskSuccess；失败、未开始和正在处理时取消需分别计数。 |
| 请求/执行期限到达 | 保留现有 deadline 分类并说明已完成部分 | 当前 deadline 属于 failed；若要另增 timed_out 需要独立 API/hook 兼容方案。 |

实施拆为三阶段：先提供文件级只读结果摘要与可验证计数，保持既有返回错误、API 终态和 hook；随后为新结果契约增加明确的适配/版本选择，并同步 API、webhook、hooks 和双语展示/文档；最后再修正 batch 的继续策略和失败项重试。第一阶段已在 `56a5bb9` 完成；第二阶段目前仅在 `509e9ea` 开放 API transfer 的请求选项，其余类型和 Telegram 展示仍待办；第三阶段未实施。摘要也需区分任务元素与预处理跳过文件，不能将仍在执行的文件当作最终成功。重试只选择明确失败项；重试同名覆盖、topic 与媒体组完整性必须单独验收，不以自动整批重跑实现。

新契约建议通过可识别的部分失败结果表达；在尚无专用部分失败 hook/API 终态时，按 failed 与 TaskFail 处理，并携带摘要，不再表示完全成功。既有调用方在明确适配前保持原行为；取消仍优先识别 context.Canceled，不能被部分失败摘要覆盖。不能只将 transfer 的 nil 改成普通错误就宣布契约完成。

本次问题核实后实施了第一阶段：batch/transfer 提供 `ResultSummary()`，快照包含输入顺序的 ID、输入文件名、状态及原始错误文本，并在 Execute 结束时记录 Info 级汇总计数。快照为独立副本，读取或修改副本不影响执行。并发操作按输入序号记录，不把重复 ID/同名文件合并。工作线程开始/结束时记录状态，最终快照在 errgroup 全部返回后取得。

### 行为与兼容边界

创建 transfer 时可显式填写顶层 `result_policy`。省略或空字符串沿用原行为：不读取文件结果 Provider，查询/Webhook 不增加结果字段；显式 `legacy` 增加计数但保留原完成结果和 hook；显式 `strict` 在 Execute 返回 nil 后检查父取消/期限及文件计数，只有全部已提交文件成功才进入 TaskSuccess/completed，部分或全部失败进入 TaskFail/failed。原始执行错误保持身份与 context 分类，不被摘要覆盖。选项仅覆盖本次请求，工厂对象通过副本传递策略，HTTP 请求结束仍不会取消已排队任务。

worker 在 Execute 确实进入并返回后读取结果、判定终态，然后执行对应 terminal hook，最后通过 taskevent 传递同一错误与计数。API 沿用 worker 的判定，不再次独立推导终态。执行前取消没有结果摘要；strict 的有效计数校验拒绝负数、不一致和整数溢出。六类计数覆盖已提交元素，预处理排除项不计入 total；没有新增 skipped 或 timed_out 终态。

API 只传输固定的七个计数，不包含输入名称、逐项错误或重试清单。每个 sink、存储快照、响应和 Webhook payload 分别持有独立计数副本；查询在同一锁内取得状态、策略和计数。提前 DELETE 仍只发送一次取消通知；执行结束可为 GET 补充最终计数并刷新 updated_at，不更改终态、不发送第二次通知。首个取消通知没有摘要时，接收端须另行查询，不能根据缺失字段认定全部成功。

`GET /api/v1/task-types` 仅为 transfer 宣告 legacy/strict；其他类型选择非空策略或任何类型填写未知策略，在列举存储/创建任务之前拒绝；空字符串按省略处理。双语 API 文档说明选项、计数、取消、deadline、旧接口与通知去重。文件执行/继续策略、失败 map、原有进度字节、已保存文件的保留规则、队列取消模型和 Telegram 展示均保持原路径；未增加自动重试、回滚或持久化。
