# 监听相册整组接纳复核

基线：dev `6113fdb5c523161e320aaffc75e53e6d459f6fef`。承接 [队列接纳契约与容量治理评估](2026-10-10-queue-admission-assessment.md)，本批完成整组接纳和监听接入，不引入容量配置。

## 问题与实施范围

原监听保存相册逐文件调用 `core.AddTask`。如果后一个提交遇到队列关闭或重复 ID，前面的文件可能已经入队并开始执行。逐项增加容量拒绝也会放大这种部分接纳问题。因此先提供整组预检和一次接纳，再单独评估容量。

`TaskQueue.AddBatch` 在同一把队列锁内检查关闭、空指针、与已有任务或组内重复 ID、已取消状态，全部通过后才按传入顺序写入 FIFO 和任务索引。重复检查仍覆盖等待及执行中任务。多成员提交 Broadcast 唤醒等待 worker；单成员仍使用 Signal。空组不改变队列，关闭后也可空调用。

`core.AddTasks` 为每个执行对象创建独立 wrapper。底层拒绝时全部 Cancel 新 wrapper 并原样返回错误，不取消 caller 或既有任务；成功后由队列管理并在 Done 释放。`AddTask` 保持单任务 API，复用相同接纳和清理路径。worker、hooks、执行结果及终态事件没有改动。

监听普通相册先按原规则构建所有能准备成功的任务，再一次提交。建目录路径仍逐个 GroupedID 收集、保留原目录与存储选择，然后每个相册单独提交。未引入等待、隐式重试或重新拼装媒体组。

## 媒体组保护与行为边界

相册缓冲键、timer 所有权、等待时间、过滤匹配、caption 选取和文件命名函数保持基线源码一致。copy/转发、topic 路由、媒体下载上传、FFmpeg、存储写入及相关依赖均保持原实现。

建目录模式沿用原行为：默认目录供 NEW-FOR-ALBUM 使用，文件单独命中的其他目录仍生效；首个有效文件的名称决定相册目录，首个有效文件的存储供组内任务使用；收集后仅剩一个成员的组仍跳过。这些行为没有借本批调整，后续若要改变，必须独立评估兼容性和真实相册联调。

原子性只涵盖“本次选定且准备成功的任务”的接纳。存储解析或任务构造失败的成员仍按原策略记录错误并跳过；接纳成功后的取消、单文件执行失败和远端写入仍独立发生。不能把本次修改称为相册保存事务，也不能保证 Telegram 迟到消息已全部发现。

监听结构化诊断区分以下状态：

| 状态 | 日志 | 关键字段 |
| --- | --- | --- |
| 有准备成功的任务并整组接纳 | Watch album tasks admitted | user_id、grouped_id、source_peer、admitted_tasks、prepare_failed |
| 整组拒绝 | Watch album admission rejected | user_id、grouped_id、source_peer、rejected_tasks、prepare_failed、error |
| 普通路径无可提交任务 | Watch album has no prepared tasks | user_id、grouped_id、source_peer、prepare_failed |

建目录收集阶段的存储选择失败按 GroupedID 计入准备失败数；没有可处理组时保留逐文件错误和原汇总日志。日志是内部诊断，不产生 Bot 回复、成功创建记录或自动重新提交。

## 回归与合入标准

新增队列测试覆盖：后续成员拒绝时无已发布前缀、等待/运行任务重复、组内重复、取消、空指针、关闭、FIFO、每个成员完成释放、三个已等待 worker 同时唤醒、并发组成员不交错，以及整组提交与 CloseAndCancel 竞争时的所有权一致性。

Core 测试通过 context.AfterFunc 的公开契约计数实际取消注册，验证重复/关闭/空成员拒绝释放每个新 wrapper、成功保留 context、独立完成释放、不取消 caller。监听测试使用真实任务构造、真实孤立队列和 Telegram 消息结构，验证两条路径的一次提交与拒绝、默认/消息命名及 caption 不变、最后匹配规则优先、目录和 GroupedID 独立性、准备失败计数及全失败不提交空组，不依赖 Telegram 网络或应用队列单例。

首轮全量普通测试和 vet 通过，Windows race 在旧 hook 测试工具中出现 `find hook fixtures: Access is denied`；该轮记为失败，日志与源码清单保留在验证目录的 initial-failure。原错误缺少具体 API 阶段，不能据此确定该次失败的根因；复核发现快照、身份查询、Go 进程句柄捕获之间存在进程退出窗口。仅加强 Windows 测试工具：查询句柄同时申请 SYNCHRONIZE，查询/捕获出错后用原句柄确认退出；确已退出则不视为存活检查失败，仍存活或状态不可验证时继续报错，并添加查询/捕获阶段与 PID 诊断。原句柄阻止 PID 重用，关闭句柄错误仍返回。新增真实子进程用例覆盖存活、已退出和无效句柄；退出后的真实 FindProcess 调用三次均未返回错误，另注入 Access denied 验证错误处理，因此不宣称已复现初始异常或证明其根因消除。生产 hook 实现不变，也不将本次防护等同于历史输出管道异常的根因修复。

最终候选源码在全量普通测试、独立 vet、全量 race 开始前重新固定 SHA-256；完成后复核源码未漂移。临时 overlays 分别撤回整组预检、足够 worker 唤醒、全部 wrapper 清理、监听整组提交及 Windows 测试退出确认，必须产生对应行为断言失败，避免测试仅覆盖函数形式。验证索引：`tmp-architecture-validation-20261009/_atomic-album-admission-20261010/`（本地忽略目录）。合入须同时满足本地验证、最终 diff 审查、候选提交 Ubuntu Quality 全成功、dev 基线未变化，并检查合入 dev 的 Quality。

## 后续评估

可继续评估默认 0（无限制）的可选等待队列容量。仍需分别完成配置校验、取消条目清理、整组容量边界、Bot i18n/监听诊断/API progress 清理及拒绝反馈，不能直接打开限制，也不把队列任务数量当成文件、临时磁盘或 Telegram RPC 预算。
