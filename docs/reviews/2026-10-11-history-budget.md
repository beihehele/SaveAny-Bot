# 网页/API 任务历史预算与后续安排（2026-10-11）

本报告接续 [rc.4 实施与验收记录](2026-10-11-remaining-implementation.md)。起点为 dev `e3cdbd6`，本批改变网页/API 内存任务记录的保留策略；rc.4 标签、镜像和当前 WSL 实例仍对应运行代码 `237b53c`。本批本地验证不能算作已发布版本的 CI 或真实 Telegram 验收。

## 复核与实施

`api/progress.go` 原先只有约 24 小时终态保留期限，短期大量完成任务仍可累积记录。后台关闭 HTTP API 时也会通过同一个 factory/store 提交保存任务，因此预算同时适用于网页与 API。当前单用户没有已证实的内存故障，本批是独立的容量保护。

网页/API 共享独立的 1000 条终态额度；保留期限仍为约 24 小时。超限按最后更新时间从旧到新淘汰，相同时间按 ID 确定顺序。注册、终态转换、列表读取和原有周期清理会执行预算；排队及仍在执行的任务不被淘汰。正在执行的任务即使已经标记 cancelled，也要等 worker 完成最终结果与 hooks 后才能进入可淘汰历史。

Webhook 的目标地址在终态决策的锁内捕获，发送及重试不再依赖后续查找历史记录。一次通知决策、原有三次重试、服务停止取消和 90 秒通知期限保持原契约。已取消任务后来的有效最终统计继续补全 GET，不改终态、不再通知。

此额度独立于 Bot 队列观察的 1000 条额度；后台按 ID 合并，两者不是后台总行数上限。活动任务、尚未退出的执行线程和在途通知也不属于已结束历史预算；本批不宣称整个进程内存或队列容量已被限制。被淘汰任务详情返回原有的 404。

中英文后台提示及 API/后台文档同步解释上述范围。没有增加配置项、数据库迁移、任务回放或自动重试。

## Review 与回归

- 检查 map/记录/队列锁的调用顺序：通知及历史清理在释放记录锁后执行；队列查询只观察是否仍在执行。没有在队列锁内更新 API 记录或改变调度。
- 覆盖到期边界、超量、按更新时间淘汰、时间相同的顺序，以及多次注册/终态转换及时清理。
- 并发覆盖八个提交者、320 次任务完成、清理与迟到事件；活动记录保留。
- 零历史额度下，终态记录立即淘汰，webhook 首次失败后重试仍保留原任务/状态/错误；迟到事件不生成第二次通知。
- 独立进程运行真实 queue/worker：Execute 阻塞时取消，强制记录超过保留期仍保留；worker 退出时收到真实最终计数，之后才能淘汰。
- 负对照只在忽略目录使用 Go overlay：去掉执行中保护触发“evicted cancelled task while Execute was still active”；破坏通知地址触发“eviction suppressed webhook or retry”。两者均为预期断言失败，工作树不包含破坏逻辑。

Windows 全量测试与 vet、API/后台/core/taskhistory/queue 竞态回归已通过；后台文案更新后相关测试通过。WSL 最终源码的 API/后台/core 全部子包/taskhistory/queue 回归、全量 vet、API/后台/database 的 SQLite 变体与编译通过；API、后台两个测试二进制在独立 Alpine 容器中以禁用外部网络的方式执行通过。两个负对照均触发指定失败，当前实现通过。本地证据位于 `tmp-month-review-20261011/history-budget/`；源码冻结清单、负对照日志和 WSL 日志不随源码或镜像发布。

本报告随历史预算批次一并提交；上述验证基于冻结的本地源码，提交时尚未推送、发布或更新 WSL 运行实例。提交前 diff review 未发现合入阻塞。用户草稿与原始会话文件的 SHA-256 均与前轮一致。

## 真实照片/视频专项（rc.4）

本轮在已获授权的私有测试源及目标 Topic 上验证，运行版本仍为 `2.0.0-rc.4 / 237b53c`，网页/API 历史预算改动没有部署。测试仅使用合成照片和短视频，本轮没有修改媒体组聚合、去重、过滤、转发、命名或保存代码。

- 相邻的两个两成员媒体组分别为照片、视频；仅首成员有 caption 且匹配过滤条件。监听本地保存 4 个文件，逐一与 Telegram 下载参考内容校验哈希，无 caption 成员继承组 caption 并带唯一消息 ID。
- 监听向 Topic 转发两组共 4 个成员；媒体标识、组边界、成员顺序、Topic、caption、富文本偏移、来源链接和移除原转发署名均核对通过。
- 网页复用的任务 API 提交四个重叠成员链接，得到 `ready / duplicate / ready / duplicate`，实际保存 4 个文件且哈希匹配；照片 `?single` 保存 1 个指定成员且哈希匹配。HTTP API 配置仍关闭，调用来自已认证的后台接口。
- 用户常用客户端提交三次 `/copy`：history 复制最新视频组，search 分别复制照片组和视频组。三个任务完成，目标新增三个完整两成员组，共 6 个成员，媒体标识、组边界、顺序、Topic、caption、富文本及来源链接均通过。
- 媒体组隔离、过期定时器、caption 命名、整组接纳及转发相关的两组竞态回归通过。真实发送的是相邻组；交错成员到达仅有确定性/竞态回归，不能标成真实网络交错验收。未刻意制造或验收真实 FLOOD_WAIT。

辅助客户端发送原先的 0.3 秒合成 MP4 组返回 `MEDIA_EMPTY`，失败定位到消息进入 Bot 前的 `messages.sendMultiMedia`。改用独立的 2 秒、320×180、H.264/AAC 合成 MP4 后发送成功。时长、分辨率、音轨同时改变，不能据此断言最小时长或唯一根因；辅助客户端偶发命令未确认的问题仍保留待查。失败样本及只发送照片的部分结果保留，已确认内容哈希的测试照片归档到独立验收目录。项目和候选运行环境没有增加 FFmpeg 依赖；合成文件由独立、无外部网络且仅挂载测试资产的工具容器生成。

**功能场景与后续清理补验均完成**：原验收脚本等待最后一条临时监听移除时超时，随后结束自有脚本并删除两个辅助会话副本；此失败历史保留原样。用户再次执行剩余的 `/unwatch` 后，独立补验确认全部临时监听已移除、队列为空、候选容器健康且重启次数为零，API 仍关闭。配置文件哈希与 rc.4 升级前备份完全一致；只读对照备份及当前数据库，users、dirs、rules、watch_chats 的数据一致（忽略 created_at / updated_at）。没有直接修改运行数据库。专项通过以独立的 `completion-verification.json` 与 `restored-state-verification.json` 为依据，不把原脚本的清理超时改写成成功。

证据位于忽略目录 `tmp-month-review-20261011/media-acceptance/` 及 WSL 私有验收目录；私有 fixture、会话、聊天内容和原始日志不随提交或发布。用户草稿及原始 Userbot 会话哈希与前轮一致。
