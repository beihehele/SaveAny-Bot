# 队列接纳契约与容量治理评估

> 这是 `be4bbaa` 时的评估。后续已合入监听相册原子接纳，逐文件入队描述保留为历史依据；容量上限尚未实施。最新状态见 [当前待办与发布验收](2026-10-10-release-readiness.md) 和 [原子接纳复查](2026-10-10-atomic-album-admission-review.md)。

基线：dev `be4bbaa5c34d37188c756a71be488b772ef6207f`。生产为单用户、Telegram/本地存储，HTTP API 仅本机或内网；当前没有隔离 Telegram 联调环境。

## 已核实的现状

`pkg/queue/queue.go::Add` 在锁内检查关闭、重复 ID 和已取消任务，然后加入 FIFO；没有容量限制，也不等待可用空间。重复 ID 检查覆盖等待和执行中任务，因为 `taskMap` 保留条目直到 `Done`。`Close` 排空已有队列，`CloseAndCancel` 中止已有工作；执行中的取消任务仍占 worker，直到 `Done`。

`core/core.go::AddTask` 每次提交创建一个新的 `queue.Task` 和 child context。关闭或重复 ID 拒绝时，原实现直接返回错误，没有调用这个新 wrapper 的 Cancel；长生命周期 parent 会保留拒绝提交的取消注册。本批只修复该失败路径。未初始化时在创建 wrapper 前返回，没有同类泄漏。

不能把失败时的 Cancel 放进 `TaskQueue.Add`：调用者可能再次传入队列已持有的同一个指针，自动 Cancel 会停止先前成功接纳的任务。Core 创建的新 wrapper 与既有 wrapper 独立，适合由 Core 清理。

相册有不同入队单位：

| 路径 | 当前入队单位 | 直接加逐项容量拒绝的影响 |
| --- | --- | --- |
| Bot 手动批量保存 `utils/shortcut/tftask.go` | 包含多个元素的一个 batchtfile 任务 | 一次接纳或拒绝；任务数上限不能限制其中的文件数 |
| 监听相册 `watch_local.go::processWatchLocalAlbum` | 普通路径逐文件建立并提交任务 | 可以只接纳前几个文件 |
| 监听相册建目录 `watch_local.go::processWatchMediaGroup` | 分组并确定目录后，逐文件提交任务 | 可以留下部分相册；各文件的目录和存储选择需保留 |
| 监听 copy/转发 | 不通过这一保存任务队列 | 单独限制任务队列不能约束全部 Telegram RPC |

现有构建任务或解析规则失败也可能跳过个别文件。后续整组接纳所保证的是“本次已选定、成功准备的任务全部入队或全部不入队”，不应声称相册发现、保存执行或远端写入具备事务性。

## 确定的所有权契约

1. `TaskQueue.Add` 返回 nil 时，队列接管 wrapper 的等待、执行和取消生命周期；worker 完成 hooks/终态事件后以 Done 释放。
2. 返回错误时，不发生新的所有权转移，队列也不取消调用者 parent 或此前接纳的任务。直接使用底层队列的调用者自行释放刚创建、尚未被接纳的 wrapper。再次提交已经接纳的同一个指针时，原队列的所有权不变，不能把它当成新建的拒绝对象取消。
3. `core.AddTask` 自己创建 wrapper；发生拒绝必须取消该 wrapper，然后原样返回入队错误。不得取消执行对象共享的 parent，不启动 hooks，不发出执行完成事件。
4. 成功提交不提前 Cancel；等待和执行中任务仍按现有 context、取消和结果契约运行。

## 后续容量方案及实施前提

采用可选等待队列容量，默认 0 表示不限制；负值拒绝配置初始化。配置应在启动 Prepare 时应用，不在本批引入热更新。容量计数按队列任务，而非文件、字节或 Telegram 相册；执行中任务另由 workers 限制。

满队列立即拒绝，不在 Bot handler、相册 timer callback 或 HTTP 请求里等待，也不隐式重试。否则等待会阻塞监听处理，并可能在 caller 已收到失败后再次接纳同一操作。队列内部应提供可用 errors.Is 识别的满队列错误，调用层再形成 Bot 文案、监听诊断和 API 状态。

先实现同一锁内的整组预检和一次提交：检查关闭、与已有任务/组内重复 ID、取消状态及容量；检查失败不新增任何条目，成功保持准备好的任务顺序并唤醒足够 worker。这里的原子性仅针对接纳，不能防止成功接纳后 caller 取消或执行失败。

监听两条相册路径必须在入队之前完成选定任务准备，再整组提交；保留当前命名、caption、过滤、规则优先级、目录、存储选择和相册分组策略。构造失败的处理需明确日志与接纳范围，不以重写聚合器实现容量治理。建目录路径也不能误将不同相册合为一个事务。

检查容量前应清理已取消的等待条目，避免无 worker 消费或外部 parent 取消时产生假满。运行中的取消任务继续计入运行任务，不提前释放 worker；Close 与 CloseAndCancel 的区别保持不变。新建的整组 wrappers 在拒绝时全部释放，成功接纳的任务由队列释放。

反馈必须区分“队列满而未接纳”和“任务执行失败”：Bot 使用 i18n；监听日志包含组标识与被拒绝任务数量，便于重新提交；API 清理已注册的 progress 项并返回明确错误，不产生成功创建记录。不能凭空估计 Retry-After，也不将入口脚本检查当成目标容器完整关停验收。

## 本批范围与后续优先级

本批实施拒绝提交的 child context 释放及所有权回归测试，不新增容量配置，不改变媒体组监听/转发代码或队列调度。随后可独立实施并审查整组接纳、两条监听相册接入及满队列反馈，验证并发、重复 ID、容量边界、取消、关停和整组不发生部分接纳后，再提供默认关闭的容量开关。

任务数量上限只能限制排队任务数，不能代替全局下载/RPC 并发、临时空间、媒体工具输出或 batch 元素预算。这些预算继续独立评估，不能因新增队列容量而宣称资源已全面有界。

正式发布仍需隔离 Telegram 相册/caption/过滤/copy/topic、目标 Linux/容器关停及停止部署副本后的备份升级恢复；历史 Windows 测试输出管道异常尚未完成根因定位。本评估不关闭这些验收项。

## 本批回归与合入判断

原实现通过新增用例复现三种拒绝路径的取消注册残留。修复后的全量普通测试、独立 vet、core/queue/API/Bot handlers 调用链 race 及专项 race 十次均通过，耗时约 247、29、83、7 秒。两个临时 overlays 分别撤回 Core 清理、在底层队列拒绝时自动 Cancel，均产生预期行为断言失败，未发生编译失败。最后复核澄清队列所有权注释：重复提交已接纳指针时，其原有所有权保持不变；此修订只涉及两行注释，另做最终源码专项检查。

与基线对照，363 个保护文件（Go 源码、依赖及 AGENTS.md）保持一致；worker、hooks、媒体组聚合、命名、caption、规则、copy/topic、存储保存和用户草案均保留。本批运行代码只改变 core.AddTask 的拒绝清理，未开启容量限制。验证与审查索引位于 tmp-architecture-validation-20261009/_queue-admission-20261010/，远端验收仍以候选提交的 Ubuntu Quality 为准。
