## 架构师视角

### 分层与扩展机制

`core.Executable` 与各存储能力接口能够支持多类下载、转存和上传任务，现阶段继续采用单进程结构有利于控制部署复杂度。`taskevent` 已让 API 进度与部分任务实现解耦，可作为后续统一结果与观测的基础。

主要结构性问题在生命周期管理。队列、客户端、配置、解析器和数据库通过全局变量连接，准备队列、开放入口、登录 Telegram、启动执行器之间缺少明确的就绪边界。退出时也缺少停止接收、取消或排空、等待任务、关闭客户端、清理临时文件的统一顺序。应先建立这些边界，再评估依赖注入和更大范围的分层调整。

任务实现仍直接包含 Telegram 编辑消息逻辑。它让界面更新进入文件 IO 的调用路径，也导致各任务重复实现不同的进度、取消和失败表现。适合逐类接入统一结果与展示适配器，每次保留旧接口和 hooks，避免全量替换所有任务。

### 数据与并发边界

存储注册表的锁、singleflight 初始化和任务 processing map 的问题已经在此前提交中改善。剩余风险主要位于真正的文件写入与业务语义：Local 的根目录约束、半成品的提交方式、同名文件的并发决策，以及 `Exists` 的布尔接口无法区分不存在和查询失败。

多层 workers 与下载 threads 会叠加并发，插件 VM 又存在独立的调度问题。当前没有吞吐、内存、磁盘和 FLOOD_WAIT 的生产测量数据，不能据此直接提高并发或更换算法。应先给出全局任务、每个存储和插件执行的容量限制及观测指标。

### 可靠性与安全

持久化配置和 SQLite 模型并不等于持久化执行任务。目前队列、API 任务记录及监听中的临时聚合状态都在内存中，UserBot 的事件通道满时会主动丢弃事件。对于个人转存，这是需要明示的运行限制；对于可靠备份和持续归档，则需要任务记录、重试与补偿、去重和恢复机制。

依赖扫描新增了需要处理的安全事项，其中 gotd 涉及 Telegram 底层。修复应保持媒体组的展开、过滤、caption、topic、排序、随机 ID 和取消占位行为，并建立独立升级批次。应用权限检查不能替代底层协议解析的长度校验。

## 产品经理视角

### 产品定位与用户承诺

建议把核心承诺收敛为“将选定消息或文件转存到配置的存储，并提供可理解的结果”。自动归档、跨存储迁移和多用户能力应分别说明可靠性、权限与恢复边界。当前缺少重启恢复和补偿机制，使用者不能仅依赖一条成功提示来判断全部文件均已保存。

最重要的使用旅程如下，按用户需要完成的事情评估，而不是按命令数量评估。

| 使用旅程 | 现状与产品问题 | 优化方向 |
| --- | --- | --- |
| 首次部署 | 文档曾遗漏会话持久化，更新步骤可能继续运行旧镜像；本轮已纠正。外部命令和浏览器可用性仍难判断。 | 最小配置、依赖检查、数据目录说明、明确的启动结果。 |
| 保存单个文件或媒体组 | 媒体组已有大量专项修复与测试；Local 最终文件的边界和原子性仍有缺陷。 | 优先保证保存结果可信，并保留媒体组行为验收基线。 |
| 批量转存 | 批量文件的 `IgnoreErrors` 没有执行效果；transfer 忽略失败时仍返回 nil。 | 分别呈现成功、失败、跳过和取消，提供失败条目与受控重试。 |
| 长期监听 | 通道满时丢事件，重启时内存中的待处理消息无法自动恢复。 | 明示可靠性边界，先增加积压和丢弃指标，再评估补偿与持久化。 |
| 查询进度和取消 | API 取消可被结束事件改写成 failed；部分 Telegram 终态仍保留取消按钮。 | 统一终态规则和反馈，取消后明确哪些输出已保存。 |
| 更新与回滚 | fork 自更新仍查上游；数据库迁移缺少恢复验证；浮动镜像使版本难复现。 | 发布来源固定、版本可追踪、升级前备份、验证恢复与回滚条件。 |
| 多用户使用 | 有用户和存储白名单，任务列表和取消没有任务所有权隔离；高级执行能力面向可信用户。 | 明确共享管理员模式；向不可信用户开放前再建设角色和任务权限。 |

建议关注提交到完成的等待时间、文件级成功率、部分失败率、取消完成时间、监听丢弃数量和更新后的验收结果。站点支持数量和命令数量不能替代这些指标。暂不需要为当前个人部署引入大型 Web 控制台或拆分微服务。

### A01 依赖与构建工具链的已知漏洞

**P1；扫描确认，gotd 分配行为已安全复现；范围中到大，风险高。** Windows 全项目源码扫描和 Linux 主程序源码扫描均报告 10 个带符号路径的不同漏洞条目。Go 标准库结果对应本次使用的 Go 1.26.4，不能据此推断生产二进制使用相同工具链。

gotd 当前为 v0.143.0。20 字节的无 payload 数据包声明 1 MiB 长度时，解码器先分配 1 MiB，再报 payload 不足；诊断刻意限制了分配大小。官方修复版本为 v0.145.1，增加分配前长度检查。影响是拒绝服务；本项目作为 Telegram 客户端，需要结合握手对端或通信路径的信任条件评估，不能理解为公众可以直接连接 Bot 的 MTProto 监听端口。[官方通告](https://github.com/gotd/td/security/advisories/GHSA-whmm-qj9r-wvr2)

建议先核实部署二进制的构建信息，再分别安排工具链修补、x/text 更新和 gotd 安全修复。gotd 如有 API 兼容问题，应评估仅回补官方补丁的成本。旧 GitHub SDK 引入的 OpenPGP 警告需要更换相关依赖链，不是提高 x/crypto 版本即可解决。验收要求为重新扫描、全量测试、各构建变体编译，以及 gotd 变动后的隔离 Telegram 媒体组联调。

### A03 Local 路径可越过配置根目录

**P1；复现；范围中，风险中。** [storage/local/local.go:49](E:/WorkSpace/Github-Projects/SaveAny-Bot/storage/local/local.go:49) 直接拼接路径；`Save` 与 `OpenFile` 都接受 `../outside.txt`，实际访问 `base_path` 之外。该结果不代表未授权用户已绕过 Bot 或 API 的认证。

### A04 Local 写入失败会留下最终名称的半成品

**P1；复现；范围中，风险中。** [storage/local/local.go:53](E:/WorkSpace/Github-Projects/SaveAny-Bot/storage/local/local.go:53) 直接创建目标再复制。reader 返回部分内容和错误时，目标文件仍存在；后续重试可能创建带后缀的新文件。检查存在性后再创建也没有并发唯一性保证，后者为代码确认的竞争风险。

应在同一目录写临时文件，成功关闭后再按覆盖或自动改名策略提交；失败清理临时文件，覆盖模式须保留原目标直到提交成功。架构收益是失败与重试可推理，产品收益是用户不会误认半成品为保存成功。验收需要断流、取消、关闭失败、覆盖失败及并发同名写入，不以改动自动改名策略代替原子提交。

### A06 停机没有完整等待与资源关闭顺序

**P1；idle worker 不响应取消已复现，其余代码确认；范围大，风险高。** [main.go:14](E:/WorkSpace/Github-Projects/SaveAny-Bot/main.go:14) 只注册 `os.Interrupt`；Linux 容器通常使用的 SIGTERM 未接入同一取消流程。[core/core.go:23](E:/WorkSpace/Github-Projects/SaveAny-Bot/core/core.go:23) 在 `queue.Get` 等待时不响应 context；[cmd/run.go:59](E:/WorkSpace/Github-Projects/SaveAny-Bot/cmd/run.go:59) 退出阶段没有等待 worker 后再清理缓存。

### A07 fork 自更新仍指向上游

**P1；代码确认；范围小到中，风险中。** [config/version.go:13](E:/WorkSpace/Github-Projects/SaveAny-Bot/config/version.go:13) 的 `GitRepo` 为上游，CLI 和 Bot 更新都使用它。有效发布版本触发更新时可能替换为不含 dev 修复的二进制；当前 `dev` 版本的 semver 检查会阻止 CLI 自更新，不能混淆这两种情况。

### A08 插件执行取消与 VM 调度不完整

**P1；满请求队列时取消失效已复现，VM 共享为代码确认的条件风险；范围中到大，风险高。** [parsers/js/js.go:41](E:/WorkSpace/Github-Projects/SaveAny-Bot/parsers/js/js.go:41) 的 `CanHandle` 没有 context 或超时；`Parse` 在进入取消 select 前先阻塞发送请求。JS 无限循环不会因为调用方停止等待而终止。

一个脚本可注册多个 parser，这些 parser 共享同一 VM，却各自启动 goroutine。Goja Runtime 要求单 goroutine 使用，应按 VM 串行调度，配合可取消入队和受控执行中断，而不是仅为等待结果增加计时器。产品上需要插件失败不会拖住所有解析请求，并保留原有返回 Error 对象和运行时注册契约。验收包括满队列、无限循环、同脚本多个 parser、超时后再次调用、HTTP 阻塞与正常插件兼容性。

### A09 CLI watch 的重新入队可阻塞 worker

**P1；复现；范围中，风险中。** [cmd/watch/uploader.go:128](E:/WorkSpace/Github-Projects/SaveAny-Bot/cmd/watch/uploader.go:128) 在同一 worker 内将需要再次上传的文件写回任务通道。当通道已满且只有一个 worker 时，worker 成为唯一消费方又阻塞在发送，无法继续处理。

应把重传调度交给独立协调逻辑，并定义 Submit、Close、正在执行和待重传之间的状态。验收包括单 worker 满队列、上传期间反复修改、退出与 timer 并发、失败重试和不重复上传。该项仅涉及本地目录 CLI watch，不是 Telegram `/watch` 或媒体组算法。
