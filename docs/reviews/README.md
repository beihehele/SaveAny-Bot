First-byte diagnosis subsequently observed intermittent Telegram DC handshakes through the proxy, including failing IPv6 candidates winning the default resolver race. With production settings unchanged, the same large file produced its first block after approximately 11.6 seconds to local storage and 4.6 seconds to ShardReel; both diagnostic tasks were cancelled and their temporary files cleaned. The original 75-second stall's exact endpoint was not recorded. Subsequent read-only OpenClash inspection confirmed rule mode, IPv6 disabled, and NAS Telegram connections matching `GeoIP: telegram` through the instant-messaging proxy group rather than DIRECT. The large-file connection used DC4 while the clients' primary sessions used DC5. This is consistent with the failed IPv6 probes, but does not identify the original stall's unique cause.

A full 1,036,238,771-byte download trial received its first block after approximately 6.7 seconds, then failed after receiving 311,427,072 bytes with `get next chunk: recovery: rpcDoRequest: engine was closed`. It produced no complete staged file and started no remote upload; no full-file hash comparison was possible. The existing discard action cleaned the failed trial, reducing cache bytes, failed-file count and reserved outbox bytes to zero. Production configuration and container start times were unchanged.

An authorized comparison temporarily selected the existing Japan node group for instant messaging, leaving other selectors unchanged. The same file completed on rc.15: first-block observation took approximately 7.1 seconds, and download, ShardReel ingest and full readback together took approximately 48.8 minutes. The independently hashed staged file, durable record, remote API receipt and complete admin-download readback all matched in size and SHA-256. DC4 connection re-establishment was observed while download progress continued. The original instant-messaging selector was restored after verification. The owned remote file and directories were permanently removed, its cloud-cleanup job completed, caches/outbox payloads were empty, three databases passed integrity checks, and 83 pre-existing file records plus configuration/preferences were preserved. Neither service nor the NAS was restarted. The full-file acceptance gap is closed for this sample; the original route's sustained reliability and the first failure's unique cause remain unestablished. No program, retry or concurrency changes were needed for this comparison; normal-use observation remains appropriate for the candidate.
